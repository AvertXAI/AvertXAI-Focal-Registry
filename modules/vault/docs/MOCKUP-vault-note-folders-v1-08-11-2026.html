Secured Notes — a real folder structure

Mockup v1 · 08-11-2026. Static HTML, nothing built. Answering “I need to create a folder structure, add it to where the notes are showing now, that way it will help me with the folder location.”
Why this is a real build and not a rail you can bolt on. Notes today have a flat text column — vault_notes.folder, one string, no nesting, no rename, nothing to click. Passwords have something completely different: vault_folders, a proper table with parent_id, counts, and a rail. So Secured Notes is not missing a UI; it is missing the model underneath it. That is also exactly why importing D:\dev\_source was disappointing — 2,000 files from a deeply nested tree all collapsed into one “Category” box.

0 · Where notes actually live — and what delete does

Jason asked both on 08-11-2026 and called them huge. They are. Answered from the code, with receipts, because a wrong answer here loses somebody's work.
THE VAULT CANNOT DELETE, MOVE, RENAME OR OVERWRITE A FILE OF YOURS. There is no code path that does it.
An audit of every filesystem call in the whole vault service layer found zero unlinkSync, rmSync, renameSync or copyFileSync. Exactly three writes exist anywhere, and none of them is a document of yours:
  • crypto.ts:36 — the vault's own key file, in the app's data folder.
  • transfer.ts:108 and :152 — the Export feature, writing to the exact file you chose in a Save dialog.
Every other filesystem call in the vault is readFileSync, statSync, readdirSync or existsSync. Read-only, all of it.
You do thisWhat actually happensYour disk
Create a note / runbook / snippet One row is inserted into vault_notes inside the encrypted vault database. It is not a file and there is no folder to find it in. notes.ts imports only a UUID helper and the database — it has no filesystem access at all. Nothing is written anywhere.
Import a folder of files Each file is read, and its text is copied into a new row. The vault holds a copy, from that moment independent of the original. Originals untouched — not moved, not modified, not marked.
Edit an imported note The row changes. The file it came from does not — there is no link back and no write-back. Untouched. The two have diverged, on purpose.
Archive a note Sets archived_at on the row. Full text kept, restorable. Untouched.
Delete a note for good DELETE FROM vault_notes WHERE id = ? — one database row, and only if it is already archived (notes.ts:76-80). The row is gone for good; that is a real loss of anything you typed IN the app. Untouched. If the note came from a file, that file is still exactly where it was.
Read the last row twice: delete is destructive to the vault and harmless to your disk.
The consequence worth planning for. A note you write in the app exists in one place — the encrypted database — so it is only as safe as your backup of it. There is no folder of markdown files to fall back on.

Two things follow, neither built yet: the vault's Export should be part of your routine, and a "write notes back out as .md files" option would give you a plain-text safety net. MindMerge is the opposite model — it watches a real folder and the files are the truth — so if you would rather notes lived as files on disk, that is a design conversation worth having before this gets big rather than after.

On the 2,000 cap you hit — already fixed, and here is the honest version. That number was a guard against picking C:\ by mistake and hanging the app; it was a guess, not a measurement, and it refused a legitimate import. It is now 25,000 and a setting (import.max_files) so it never needs a build to change.

A ceiling still exists because the walk is cheap but the import is not — it reads every file. At 2,041 files that is fine. If you ever point it at something genuinely enormous, the honest fix is a progress bar with a Stop button, not a bigger number.

3 · What each action does — and what it never does

The rules, so folders cannot quietly eat a note. Same doctrine the Passwords rail already follows.
ActionWhat happensWhat does NOT happen
New folderCreated empty, at the top level or inside whatever is selected.—
RenameThe folder's name changes. Notes are untouched.Nothing on your disk is renamed. The vault holds copies.
Move a folderRe-parented with its whole subtree.Cannot be dropped inside itself — the tree stays a tree.
Drag a note inThat note's folder changes. One note, one folder.No copy is made. It moves, it does not duplicate.
Delete a folderThe folder goes; its notes move to Unfiled, its subfolders move up one level.A note is NEVER deleted by deleting a folder. Confirm dialog says the count out loud.
Archive a noteMoves to the Archived shelf, remembering its folder.Restoring puts it back in the same folder, not Unfiled.
The delete rule is the important one and it matches the Passwords rail exactly: a container is not its contents.

4 · What it costs to build

So the size is on the table before you say go.
PieceWhat is involved
SchemaNew vault_note_folders table (id, uuid, org_id, name, parent_id, sort_order) plus a guarded ADD COLUMN folder_id on vault_notes. Additive and re-runnable, per the migration rule.
The existing text columnKept, not dropped — dropping is banned, and it is the migration path: on first run, every distinct folder string becomes a top-level folder and its notes get the matching folder_id. Nothing to do by hand, nothing lost.
ServicesCreate, rename, move, delete-and-reflow, list-with-counts. A close copy of folders.ts, which already solves all of it for Passwords.
Import mappingTurn each file's relative path into a folder chain, create missing links, reuse existing ones. The walk already returns rel, so the data is there.
UIThe tree column above, the breadcrumb, drag-to-move, and the three-option import step.
Three questions before I build it.

1 · Should Notes share the Passwords folder tree, or have its own? My lean is its own — “Financial” and “Photography” are password folders, and a tree holding both credentials and 2,000 markdown files gets unusable fast. Separate trees, same behaviour.

2 · One folder per note, or many? Lean: one. Tags do the many-places job better, and a note in two folders makes “delete this folder” ambiguous. Say if you want tags too — that is a separate, smaller build.

3 · Do Runbooks and Snippets share the tree with Notes, or get their own? Lean: share it. They are one stored shape with three list styles, and three parallel trees over the same table would be three places to file the same thing.
