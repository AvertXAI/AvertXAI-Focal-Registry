Three options that need your call, because they change what the log is FOR.
  • Clear resolved — should the log ever be clearable by hand? Canon says keep everything, and a log you can quietly empty is worth less when something goes wrong. My lean: no manual clear, only the level floor.
  • Export .log — plain text to a file you can send. My lean: yes, and it is the thing a bug report should attach.
  • Retention — nothing prunes this today, so it grows for ever. My lean: keep errors and warnings for ever, and roll info/debug off after 30 days, since those are volume and not evidence.

Buys back ~52 pixels of a tab strip that is already tight at the 740 floor, and removes a page that currently teaches a new user nothing. Costs one ruling to reverse later if a home page turns out to be wanted.
My lean: A, and only A. Recent activity is the one thing the other four tabs structurally cannot show — each of them is a single kind of thing, and "what happened lately" cuts across all of them. It is also nearly free: the access log and the event log already carry every row it would render.

B is a good idea in the wrong place — "needs attention" belongs on Health, where the fixes already live. C restates the sidebar two inches to its right. And D is a perfectly respectable answer: if you would not open a recent-activity page, the honest move is to delete the tab rather than decorate it.

3 · Code files — what works today, and what does not

You asked about .py files: capture as snippets, and view them in an editor.
  • Importing them: not yet, and it is one line. .py is not in the walk list — that list currently ends at markdown, text, data and the binary stubs. Any text extension can join it.
  • Storing them: already correct. A code file is text; it lands in a note wrapped in a fenced block, the same way .json and .csv already do, so nothing is lost or reformatted.
  • Viewing them: works, in monochrome. The Markdoc renderer draws fenced code with a copy button and keeps whitespace exactly. What it does not do is colour the syntax.
  • Editing them: works, with a caveat worth stating. Milkdown edits the note; the note is a copy. Editing a .py note does not touch the .py file on your disk — same one-way rule as everything else imported.
Syntax colouring is the only real decision. It needs a highlighter, and that is a §2.10 dependency call — Shiki is accurate but ships a large grammar set, Prism and highlight.js are lighter and both MIT. My lean: ship monochrome first, because a fenced Python file is perfectly readable in a monospace font, and only add a highlighter if you find yourself squinting. It is a one-file change either way.
